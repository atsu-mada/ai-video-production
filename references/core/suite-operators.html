Suite Operators

A suite operator is an execution skill that drives exactly one AI creative suite (for example a generation platform reached through MCP, an API, a CLI, or a logged-in browser UI). Preproduction skills such as this one stay suite-neutral: they author references, storyboards, prompts, and a generation handoff. The handoff's Suite: field names the operator skill that will execute it. Tool names, model slugs, credit prices, and UI steps live in the operator, never here.

The nine-heading contract

Every suite operator SKILL.md documents these sections with exactly these headings, in this order, so that an agent can compare suites without reading each one end to end. Start from the suite-operator template.

  1. Access path — MCP, API, CLI, or Chrome UI; who owns authentication; what the agent may and may not click or call.
  2. Models & modes — available video, image, and audio models; supported modes (text-to-video, image-to-video, reference-to-video, first/last frame, extend) and mutually exclusive combinations.
  3. References — accepted reference types (image, video, audio, character), count limits, tagging syntax, and minimum lengths.
  4. Limits — durations, resolutions, aspect ratios, concurrency, and file-size or upload limits.
  5. Cost estimation — how to estimate before running, known gaps between estimate and actual charge, and the approval gate (quote, user OK, run).
  6. Moderation & failure — what a block looks like, whether it is charged, and the retry and rewording procedure.
  7. Post-processing — upscale or enhance modes and which content each suits.
  8. Retrieval — how to wait for results, register downloads, and name versioned files.
  9. Approval gates — previz must be visually approved by the user before paid generation; every paid step needs a quoted estimate.

Record every limit and price as "observed YYYY-MM" with a verify-live caveat. Never write account balances, share URLs, account handles, or project names into an operator skill.

Shared client contract

  • Input is one reviewed generation handoff whose Suite: equals the operator's skill name. If it names another suite, stop and route instead of translating silently.
  • A handoff is not an order to run. The operator quotes cost, waits for an explicit user OK, and only then submits.
  • Report provider state, technical QC, and perceptual review as separate evidence states (see validation).
  • Never regenerate a queued or running job; search for existing results before re-running or re-upscaling.
  • Download every accepted output to a new versioned path; never overwrite an accepted version.
  • Keep internal job identifiers out of user-facing messages unless asked.

Naming policy

Operator skill names follow <service>[-chrome]-<action>-<role>:

  • -chrome appears only when the skill operates a browser UI.
  • <action> is omitted for a whole-suite operator (for example <service>-operator).
  • <role> is one of operator, publisher, generator, or maker.

Choosing a suite

  1. Capability fit — the required mode exists (for example reference-to-video with a previz video, or first/last frame for a partial retake) and the target duration and resolution fit one job.
  2. Reference types — the suite accepts every reference role the handoff needs (image, video, audio, character) within its count limits. Note exclusive combinations such as boundary frames versus general references.
  3. Cost — compare the quoted per-second or per-job cost, including known estimate gaps and post-processing, against the remaining budget the user states.
  4. Availability — authentication works, the access path is permitted for the agent, and queues or usage limits will not block the schedule.

Record the choice and its reason in the handoff. When two suites fit, prefer the one whose failure and retrieval behavior is documented in its operator skill.
